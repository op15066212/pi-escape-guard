= 四、新误伤三条（任务 2 的答案）

C3c 用的是**行形状**（`^\s*(?:[\w.$-]+\s+)*[\w.$-]+\s*[:=]`），它挡的是「赋值行」，不是「代码」。
凡是代码但不长成赋值行的，一律放行：

  console.log("\u4f60\u53ef\u4ee5");      → points=1，还原成 console.log("你可以");
  {"msg": "\u4f60\u597d\u4e16"}          → points=1，还原成 {"msg": "你好世"}
  名字=\u4f60\u597d\u4e16                  → points=1（\w 不含中文，中文 key 的 properties 行不被认成赋值行）

为什么这三条比上轮的 properties 更常见：JSON 资源文件、`expect(x).toBe("...")`、数组元素、
模板字符串实参——它们都是「代码里写了转义」，但行首不是 `key=`。
第二条尤其直接：那是**数据文件整行**，还原后 JSON 仍合法（JSON 允许 \u），
但一个要求 ASCII 的 .json（Android `strings.json`、i18n 资源）就被改成了 UTF-8 字面量。

改法（把代理换成直接证据，不要再加一条行形状）：

  C3d：段的前一个或后一个字符是 `"` `'` 或反引号 → 判代码，不动。
  理由：赋值行是「代码」的代理，引号是直接证据。`console.log("X")`、`{"k":"X"}`、`["X",`
  三种都满足「段紧邻引号」，而散文里的 `\u4f60` 通常两侧是汉字或空格。
  `名字=\u4f60\u597d\u4e16` 那类仍漏（它两侧是 `=` 与行尾），可以留给 C5/交还，或在 C3c 里
  把 `\w` 换成 `[^\s]`（key 允许中文）——但那样会把「正文：这里写\u4f60」也当成赋值行，
  所以我建议只加 C3d，不宽 C3c。
